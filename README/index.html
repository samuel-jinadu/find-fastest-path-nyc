01 — The Problem

Four hard problems at once

Both sources tick every 15 minutes. Beyond that, they are as different as they can be.

1
Retention

Asymmetric loss

Taxi files are deleted after 59 minutes. A scheduler gap of two hours means that window is permanently gone. Citi Bike can be recovered; taxi cannot. The pipeline cannot treat them symmetrically.

2
Units

Lat/lon vs. zone IDs

Citi Bike reports station coordinates. Taxi reports taxi zone IDs. Without a reference-data join, the two datasets cannot be compared at all.

3
Ingestion

Two protocols

One source is an authenticated REST API. The other is a directory listing plus per-file fetches. A single SimpleHttpOperator will not do.

4
Correctness

Idempotent reruns

Re-running the 14:15 interval must not duplicate rows, must not double-count, and must produce the same result whether it runs once or five times.

Lake layout

datalake/
├── raw/
│   ├── citibike/{YYYYMMDDTHHMMSS}.json      # exactly what the API returned
│   └── taxi/{MM-DD-YYYY-HH-MM-SS}.csv       # exactly what the file share served
└── processed/
    ├── citibike/{YYYYMMDDTHHMMSS}.parquet   # conformed, zone-mapped
    └── taxi/{YYYYMMDDTHHMMSS}.parquet       # conformed
Why raw first? Because taxi files are deleted after 59 minutes, the raw layer is the only copy of that window that will ever exist. Storing raw first is what makes the pipeline re-processable: change the transformation, re-run process_* against the same bytes — never re-hit the API.
04 — The Operators

Two operators carry the load

Both sources share the same shape; the differences live in the callables passed in.

Composition: input_callable → [transform_callable] → output_callable. The only contract is “DataFrame in, DataFrame out.” Swapping pd.read_json for pd.read_parquet is a keyword change, not a rewrite.

class PandasOperator(BaseOperator):
    template_fields = (
        "_input_callable_kwargs",
        "_transform_callable_kwargs",
        "_output_callable_kwargs",
    )

    def execute(self, context: Context):
        df = self._input_callable(**self._input_callable_kwargs)
        logging.info("Read DataFrame with shape: %s.", df.shape)

        if self._transform_callable:
            df = self._transform_callable(df, **self._transform_callable_kwargs)
            logging.info("DataFrame shape after transform: %s.", df.shape)

        self._output_callable(df, **self._output_callable_kwargs)

Idempotency primitive. Loads a processed Parquet object into Postgres with a single transaction wrapping DELETE-then-INSERT. Re-running the 14:15 interval deletes the 14:15 slice and re-inserts it — atomically.

df["airflow_execution_date"] = pd.Timestamp(
    context["data_interval_start"].timestamp(), unit="s"
)

engine = PostgresHook(postgres_conn_id=self._postgres_conn_id)\
    .get_sqlalchemy_engine()

with engine.begin() as conn:
    conn.execute(
        f"DELETE FROM {self._postgres_table} "
        f"WHERE airflow_execution_date='{context['data_interval_start']}';"
    )
    df.to_sql(self._postgres_table, con=conn,
              index=False, if_exists="append")
Fixed since the previous baseline: DELETE + INSERT previously ran as two separate statements. Both now execute inside one with engine.begin() as conn: block, making per-run replacement atomic.
05 — Scheduling & Idempotency

Every run knows its own interval

schedule=CronDataIntervalTimetable("*/15 * * * *", "UTC"),
start_date=pendulum.today("UTC").add(days=-1),
catchup=False,

data_interval_start and data_interval_end are used as three things:

Filenames

Deterministic keys

raw/citibike/{{ data_interval_start | ts_nodash }}.json — re-runs land on the same key and overwrite (replace=True) instead of accumulating.

Filtering

Taxi mtime window

_download_taxi_data only fetches files whose mtime falls in [data_interval_start, data_interval_end) — not the whole directory.

Serving

Idempotency key

The airflow_execution_date column makes per-run DELETE + INSERT safe to repeat any number of times.

Why catchup=False? The raw layer is append-only and the taxi source cannot be backfilled anyway — historical runs have nothing to catch up on.

Conformance: the step that makes comparison possible

transform_citi_bike_data downloads the NYC taxi-zone shapefile and performs a spatial join of Citi Bike station points against taxi zone polygons. The output columns start_location_id / end_location_id are now in the same units as the taxi data.

df_with_zones = geopandas.sjoin(start_gdf, taxi_zones, how="left")\
    .rename(columns={"LocationID": "start_location_id"})
end_zones = geopandas.sjoin(end_gdf, taxi_zones, how="left")
df_with_zones["end_location_id"] = end_zones["LocationID"]

This is the reference-data join that turns a pile of API responses into a dataset.

What is not data engineering

Being honest about scope matters. Much of the repo is demo scaffolding or adjacent disciplines:

Mock source systems

taxi_db/ and citibike_db/ are Docker images with baked-in 2023 data and a year_offset that pretends 2023 is “now”. In a real deployment these would be actual upstream databases.

Mock external interfaces

taxi_fileserver/ (nginx + cron) and citibike_api/ (Flask) simulate an external file share and an external REST API. Real ones are managed by someone else.

Consumer surface

nyc_transportation_api/ and index.html are reporting/BI — not pipeline concerns. The hard-coded taxi_zones dict is domain lookup data.

Dev-environment plumbing

The iptables-legacy FORWARD fix and the GHCR matrix build are DevOps and CI, not DE. But they are what makes the stack runnable at all.

Where the data engineering actually lives: the ingestion logic, the DAG, the two custom operators, the data contracts, the raw/processed layering, the conformance join, and the idempotent serving primitive.
