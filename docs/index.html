01 — The Data Engineering Problem

Four hard problems at once

Two sources, both ticking every 15 minutes — otherwise as different as they can be. The payload is the question; the engineering is the answer.

1
Retention

Asymmetric loss

Taxi files are deleted after 59 minutes. A two-hour scheduler gap means that window is permanently gone. Citi Bike can be recovered; taxi cannot. The pipeline cannot treat them symmetrically.

2
Units

Lat/lon vs. zone IDs

Citi Bike reports station coordinates. Taxi reports taxi zone IDs. Without a reference-data join the two datasets cannot be compared at all.

3
Ingestion

Two protocols

One source is an authenticated REST API returning JSON. The other is a directory listing plus per-file CSV fetches. A single SimpleHttpOperator will not do.

4
Correctness

Idempotent reruns

Re-running the 14:15 interval must not duplicate rows, must not double-count, and must produce the same result whether it runs once or five times.

The coupling that matters: because taxi retention is 59 minutes, DAG cadence and scheduler uptime are tied directly to source retention. A slower schedule loses data; a faster one duplicates API calls.
02 — The Two Sources

Two systems, one contract each

These guarantees drive every design decision downstream — cadence, layering, and backfill.

🚲 Citi Bike API 🚕 Yellow Cab fileserver
Interface REST — GET /recent/minute/15 Static share — GET / returns a JSON listing
Auth HTTP Basic (citibike:cycling) None
Format JSON list of ride objects CSV — one file per 15-minute window
Location unit Latitude / longitude of start & end stations Taxi zone IDs (pickup / dropoff)
Cadence Request-driven; source DB updates continuously New file every 15 min, via cron
Retention Full 2023 dataset in DB, shifted to “now” Deleted after 59 min
Backfill Possible — query further back Impossible beyond ~1 hour
Why this is a DE problem, not an API problem: one source is lossy and unbackfillable, the other is recoverable. The pipeline must record the lossy one first and treat both as interval-scoped rather than “whatever is there right now.”

04 — The Operators

Two operators carry the load

Both sources share the same shape; the differences live in the callables passed in.

Composition: input_callable → [transform_callable] → output_callable. The only contract is “DataFrame in, DataFrame out.” Both sources share this operator; swapping pd.read_json for pd.read_parquet is a keyword change, not a rewrite.

class PandasOperator(BaseOperator):
    template_fields = (
        "_input_callable_kwargs",
        "_transform_callable_kwargs",
        "_output_callable_kwargs",
    )

    def execute(self, context):
        df = self._input_callable(**self._input_callable_kwargs)
        logging.info("Read DataFrame with shape: %s.", df.shape)

        if self._transform_callable:
            df = self._transform_callable(df, **self._transform_callable_kwargs)
            logging.info("Shape after transform: %s.", df.shape)

        self._output_callable(df, **self._output_callable_kwargs)

Idempotency primitive. Loads a processed Parquet object into Postgres with a single transaction wrapping DELETE-then-INSERT. Re-running the 14:15 interval deletes the 14:15 slice and re-inserts it — atomically.

df["airflow_execution_date"] = pd.Timestamp(
    context["data_interval_start"].timestamp(), unit="s"
)

engine = PostgresHook(postgres_conn_id="result_db").get_sqlalchemy_engine()

with engine.begin() as conn:            # one transaction
    conn.execute(
        f"DELETE FROM {table} "
        f"WHERE airflow_execution_date='{ts}';"
    )
    df.to_sql(table, con=conn, index=False, if_exists="append")
Why it matters: DELETE + INSERT as two separate statements can leave the serving table empty for an interval if the second one fails. Wrapping both in with engine.begin() makes per-run replacement atomic — the rerun guarantee.
05 — Scheduling & Idempotency

Every run knows its own interval

Interval-scoped execution is what makes the whole pipeline re-runnable.

schedule = CronDataIntervalTimetable("*/15 * * * *", "UTC")
start_date = pendulum.today("UTC").add(days=-1)
catchup = False
Filenames

Deterministic keys

raw/citibike/{{ data_interval_start | ts_nodash }}.json — re-runs land on the same key and overwrite (replace=True) instead of accumulating.

Filtering

Taxi mtime window

_download_taxi_data only fetches files whose mtime falls inside [data_interval_start, data_interval_end) — not the whole directory listing.

Serving

Idempotency key

The airflow_execution_date column makes per-run DELETE + INSERT safe to repeat any number of times.

Why catchup=False? The raw layer is append-only and the taxi source cannot be backfilled anyway — historical runs have nothing to catch up on.
